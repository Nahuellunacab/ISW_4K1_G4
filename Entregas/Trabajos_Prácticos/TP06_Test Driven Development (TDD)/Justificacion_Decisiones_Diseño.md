# Documento de Justificación de Decisiones de Diseño

En el presente trabajo se optó por aplicar la metodología **Test-Driven Development (TDD)** como pilar central del proceso de desarrollo. Esta elección se fundamenta en la necesidad de asegurar calidad y robustez en el software desde las etapas iniciales. Mediante TDD, cada nueva funcionalidad se construye a partir de la redacción previa de pruebas automáticas que describen el comportamiento esperado. De este modo, los tests no solo cumplen la función de validar el código, sino que se convierten en una forma de documentación viva, capaz de reflejar las reglas de negocio y los escenarios de uso del sistema. Este enfoque favorece la detección temprana de errores, fomenta un diseño modular y obliga a pensar en la interfaz pública de cada componente antes de su implementación.

La arquitectura general adoptada se basa en la separación de responsabilidades entre frontend, backend y base de datos. Esta división responde a la intención de mantener un sistema escalable y fácilmente mantenible, en el cual cada capa pueda evolucionar sin generar dependencias rígidas con las demás. Tal decisión resulta coherente con las buenas prácticas de ingeniería de software, ya que facilita la colaboración entre diferentes integrantes del equipo y permite reemplazar tecnologías en caso de ser necesario. Así, se logra un sistema más flexible, capaz de adaptarse tanto a las exigencias académicas como a posibles ampliaciones futuras.

Para la construcción del backend se eligió **Python** con el framework **Flask**. La elección se justifica por tratarse de una herramienta liviana, flexible y de rápido aprendizaje, que se integra con facilidad con motores de base de datos como SQLite3. Además, Flask presenta una estrecha compatibilidad con los principales entornos de testing en Python, lo que resulta fundamental dentro de la estrategia TDD. Como complemento, se adoptó el estándar de codificación **PEP8**, ampliamente aceptado en la comunidad, que garantiza uniformidad, legibilidad y calidad en el código escrito. Esta convención no solo mejora la comunicación entre los miembros del equipo, sino que facilita la incorporación de herramientas automáticas de análisis estático.

En lo que respecta al almacenamiento de datos, se seleccionó **SQLite3** como motor de base de datos. La decisión responde a la necesidad de contar con una solución simple, liviana y sin requerimientos de instalación de un servidor adicional. Dado que se trata de un proyecto académico y de prototipado, esta elección resulta apropiada, pues simplifica la infraestructura y reduce la complejidad en el despliegue. No obstante, la estructura definida permite una migración futura hacia un motor más robusto, como PostgreSQL o MySQL, en caso de que la aplicación requiera mayor capacidad de procesamiento o concurrencia.

En cuanto al frontend, se optó por **React** acompañado de **Vite** como herramienta de construcción. React proporciona un paradigma basado en componentes reutilizables, lo que mejora la organización del código y la mantenibilidad de la interfaz. Por su parte, Vite ofrece un entorno de desarrollo moderno y eficiente, con tiempos de compilación reducidos y optimizaciones pensadas para la producción. Para asegurar la consistencia y la claridad en el código del frontend, se adoptó la guía de estilo de **Airbnb**, que establece convenciones estrictas en aspectos como el uso de props, el manejo de hooks y la estructura de JSX. Esta decisión contribuye a que el código sea legible y predecible, facilitando la colaboración en equipo y alineando el proyecto con estándares utilizados en la industria.

Los **tests** constituyen un eje fundamental de este proyecto. A través de ellos se documenta de manera explícita el comportamiento esperado de cada componente, tanto en el backend como en el frontend. En el backend, las pruebas permiten validar la lógica de negocio expuesta por la API Flask, verificando que cada endpoint responda con los datos y estados correctos ante entradas válidas o inválidas. En el frontend, los tests aseguran que los componentes de React se rendericen adecuadamente, respeten las reglas de interacción y gestionen correctamente el estado. De esta manera, las pruebas no solo actúan como mecanismo de validación, sino también como una guía clara para el mantenimiento futuro, ya que expresan en código cuáles son los requisitos que el sistema debe cumplir. Cabe destacar que, en la práctica de TDD, los tests anteceden a la implementación, lo que obliga a pensar primero en el diseño del sistema desde la perspectiva del usuario final y evita la incorporación de funcionalidades innecesarias.

Finalmente, se decidió incorporar **Node.js** como entorno de ejecución auxiliar, principalmente para la gestión de dependencias mediante npm y el uso de herramientas de soporte como ESLint. Esta inclusión permite integrar de forma ágil librerías modernas en el frontend y mantener un flujo de trabajo alineado con las prácticas actuales de desarrollo de software.

En conclusión, todas las decisiones de diseño tomadas —desde la metodología TDD, pasando por la elección de lenguajes y frameworks, hasta la adopción de estándares de estilo— se encuentran orientadas a garantizar la **calidad, mantenibilidad y coherencia** del sistema. Los tests, en particular, se convierten en el eje articulador de este proceso, ya que aseguran que el producto cumpla sus requisitos y actúan como la principal forma de documentación técnica. De este modo, el trabajo realizado no solo cumple con los objetivos planteados, sino que sienta bases sólidas para su evolución futura.
